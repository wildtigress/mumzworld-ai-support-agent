# 🤖 Mumzworld AI Support Assistant

Multilingual (English + Arabic) customer support triage system with structured outputs, RAG grounding, and safety guardrails

---

## 🚀 Problem

Mumzworld serves a diverse customer base across **English and Arabic speakers**, where support queries are:

* Unstructured
* Multilingual (often mixed-language)
* Incomplete or ambiguous

Typical examples:

* “I want to return this المنتج”
* “Where is my refund?”
* Nonsense or vague inputs

This creates challenges:

* Slow manual triage
* Inconsistent responses
* Risk of hallucinated answers from AI systems

---

## 💡 Solution

This project builds a **safe, structured AI support assistant** that:

* Classifies customer intent
* Generates **bilingual responses (EN + AR)**
* Grounds answers using **retrieval (RAG)**
* Detects uncertainty and escalates when needed
* Returns **strict, validated JSON output**

---

## 🧠 System Architecture

```
User Input
   ↓
Language Detection
   ↓
Context Retrieval (RAG)
   ↓
Prompt Construction
   ↓
LLM (Groq - LLaMA 3.3 70B)
   ↓
JSON Extraction
   ↓
Schema Validation (Pydantic)
   ↓
Post-processing (Arabic check + confidence)
   ↓
Final Structured Output
```

---

## ⚙️ Key Features

### ✅ Structured Output (Schema Validation)

* Enforced using **Pydantic**
* Prevents malformed responses

```json
{
  "intent": "return",
  "reasoning": "...",
  "reply": {
    "en": "...",
    "ar": "..."
  },
  "requires_human": true,
  "confidence": 0.4
}
```

---

### 🌍 Multilingual Support (EN + AR)

* Supports English, Arabic, and mixed input
* Ensures valid Arabic output

---

### 📚 Retrieval-Augmented Generation (RAG)

* Keyword-based retrieval over policy data
* Grounds responses in real context
* Reduces hallucination

---

### 🛑 Uncertainty Handling

* No context → escalate
* Ambiguous query → escalate
* Never guesses

---

### 📊 Engineered Confidence

* Based on:

  * Context availability
  * Escalation status
* Not generated by LLM

## ⚠️ Limitations

* No multi-turn memory
* No semantic search (keyword-based RAG)
* Limited dataset

---

## ⚖️ Tradeoffs

### 1. Keyword-based RAG vs Embedding-based Retrieval

**Choice:**
Used simple keyword-based retrieval instead of vector embeddings.

**Why:**

* Faster to implement within ~5 hour constraint
* Fully deterministic and easy to debug
* Sufficient for structured policy queries

**Tradeoff:**

* Less robust to semantic variation
* Doesn’t scale well to large datasets

**Future improvement:**

* Replace with embedding-based semantic search (FAISS / OpenSearch)

---

### 2. Strict Schema Validation vs Flexible Output

**Choice:**
Enforced strict JSON output using Pydantic schema.

**Why:**

* Prevents malformed outputs
* Enables reliable downstream usage
* Makes evaluation measurable

**Tradeoff:**

* Requires fallback when validation fails
* Reduces flexibility slightly

**Future improvement:**

* Add retry + auto-correction loop

---

### 3. Conservative Escalation vs Full Automation

**Choice:**
System escalates when uncertain.

**Why:**

* Avoids hallucination
* Safer for real-world support

**Tradeoff:**

* More escalations than necessary
* Less automation coverage

**Future improvement:**

* Add smarter confidence thresholds

---

### 4. Engineered Confidence vs LLM-generated Confidence

**Choice:**
Confidence is computed programmatically.

**Why:**

* LLM confidence is unreliable
* Deterministic and explainable

**Tradeoff:**

* Less nuanced scoring

**Future improvement:**

* Add calibration techniques

---

### 5. Stateless Pipeline vs Conversational Memory

**Choice:**
No conversation memory.

**Why:**

* Simpler design
* Easier debugging

**Tradeoff:**

* No multi-turn handling

**Future improvement:**

* Add session memory

---

### 6. Single LLM Call vs Multi-step Agent

**Choice:**
Single structured call instead of agent loops.

**Why:**

* Predictable output
* Easier validation

**Tradeoff:**

* Less flexible workflows

**Future improvement:**

* Add tool-based agent flows

---
