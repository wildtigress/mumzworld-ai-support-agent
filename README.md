🤖 Mumzworld AI Support Assistant

Multilingual (English + Arabic) customer support triage system with structured outputs, RAG grounding, and safety guardrails

🚀 Problem

Mumzworld serves a diverse customer base across English and Arabic speakers, where support queries often include:

Returns & refunds
Shipping questions
Mixed-language input
Incomplete or vague queries

A typical challenge:

Customer messages are unstructured, multilingual, and sometimes ambiguous

This leads to:

Slow triage
Inconsistent responses
Risk of hallucinated answers from AI systems
💡 Solution

This project builds a safe, structured AI support assistant that:

Classifies customer intent
Generates bilingual responses (EN + AR)
Grounds answers in policy context (RAG)
Detects uncertainty and escalates when needed
Outputs strict, validated JSON
🧠 System Architecture
User Input
   ↓
Language Detection
   ↓
Context Retrieval (RAG)
   ↓
Prompt Construction
   ↓
LLM (Groq - LLaMA 3.3 70B)
   ↓
JSON Extraction
   ↓
Schema Validation (Pydantic)
   ↓
Post-processing (Arabic check + confidence)
   ↓
Final Structured Output
⚙️ Key Features
✅ 1. Structured Output (Schema Validation)
Enforced using Pydantic
Prevents malformed or partial responses
{
  "intent": "return",
  "reasoning": "...",
  "reply": {
    "en": "...",
    "ar": "..."
  },
  "requires_human": true,
  "confidence": 0.4
}
🌍 2. Multilingual Support (EN + AR)
Handles:
English
Arabic
Mixed input ("return this المنتج")
Ensures Arabic output is always valid
📚 3. Retrieval-Augmented Generation (RAG)
Query-aware keyword-based retrieval
Prevents hallucination by grounding responses in policy context

Example:

“return” → return policy
“refund” → refund timeline
🛑 4. Uncertainty Handling (Critical)
If context is missing → system refuses
If query is unclear → escalates
Never guesses beyond available data
📊 5. Engineered Confidence (Not hallucinated)
Based on:
Context availability
Escalation status
Not generated by LLM
🧪 6. Evaluation System
Automated test cases (eval.py)
Covers:
Happy paths
Arabic queries
Nonsense input
Out-of-scope queries

⚠️ Known Failure Cases
Multi-intent queries (e.g., return + complaint in one message)
Deep conversational context (no memory)
Limited policy dataset (small RAG scope)
⚖️ Tradeoffs
Why simple RAG instead of embeddings?
Faster to implement in 5-hour constraint
Deterministic and explainable
Sufficient for policy-based queries
Why strict JSON output?
Ensures reliability
Enables downstream automation
Avoids free-text ambiguity
Why conservative escalation?
Safer for customer support
Avoids hallucination risk

Safety and Robustness

This system includes:

Safe language detection
Schema validation
JSON extraction
Arabic response enforcement
Human escalation for invalid or uncertain inputs

This prevents crashes, hallucinations, and malformed outputs.

Limitations
Retrieval uses simple FAQ lookup instead of semantic search
No vector database
No persistent memory or feedback loop
No fine-tuning

These were intentional tradeoffs to prioritize reliability, simplicity, and speed.
