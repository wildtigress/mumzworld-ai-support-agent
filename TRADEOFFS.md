## ⚖️ Tradeoffs

### 1. Keyword-based RAG vs Embedding-based Retrieval

**Choice:**  
Used simple keyword-based retrieval instead of vector embeddings.

**Why:**  
- Faster to implement within ~5 hour constraint  
- Fully deterministic and easy to debug  
- Sufficient for structured policy queries (returns, refunds, etc.)

**Tradeoff:**  
- Less robust to semantic variation (e.g., “money back” vs “refund”)  
- Doesn’t scale well to large or messy datasets  

**Future improvement:**  
- Replace with embedding-based semantic search (FAISS / OpenSearch)

---

### 2. Strict Schema Validation vs Flexible Output

**Choice:**  
Enforced strict JSON output using Pydantic schema.

**Why:**  
- Prevents malformed or partial outputs  
- Enables reliable downstream automation  
- Makes evaluation measurable  

**Tradeoff:**  
- Requires retries or fallback when model fails schema  
- Slightly reduces flexibility of responses  

**Future improvement:**  
- Add retry + auto-correction loop for invalid outputs  

---

### 3. Conservative Escalation vs Full Automation

**Choice:**  
System escalates to human when uncertain or context is missing.

**Why:**  
- Avoids hallucination (critical for customer support)  
- Prioritizes correctness over completeness  
- Aligns with real-world support systems  

**Tradeoff:**  
- May escalate more than necessary  
- Reduces automation coverage  

**Future improvement:**  
- Add confidence thresholds + partial automation flows  

---

### 4. Engineered Confidence vs LLM-generated Confidence

**Choice:**  
Confidence score is computed programmatically, not generated by the model.

**Why:**  
- LLM confidence is unreliable and often misleading  
- Deterministic scoring improves trust and explainability  

**Tradeoff:**  
- Less nuanced than probabilistic models  
- Doesn’t capture subtle uncertainty  

**Future improvement:**  
- Combine with model logits or calibration techniques  

---

### 5. Stateless Pipeline vs Conversational Memory

**Choice:**  
No conversation history or memory.

**Why:**  
- Simpler architecture  
- Easier evaluation and debugging  
- Fits within time constraint  

**Tradeoff:**  
- Cannot handle multi-turn conversations  
- No personalization  

**Future improvement:**  
- Add session memory or conversation state  

---

### 6. Single LLM Call vs Multi-step Agent

**Choice:**  
Used a single structured LLM call instead of an agent with tool loops.

**Why:**  
- More predictable output  
- Easier to validate and control  
- Faster to implement  

**Tradeoff:**  
- Less flexible for complex workflows  
- No dynamic tool usage  

**Future improvement:**  
- Introduce agentic flow for tasks like order lookup or tracking
